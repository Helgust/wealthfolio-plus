## Короткий ответ

С форком ignidash красивый интерфейс появится быстрее, но в целом проще не станет.

1. **Самое трудное для Испании у нас уже сделано.** Налоговое ядро на Python: IRPF по двум базам и двум
   половинам, mínimos, reducciones, перенос убытков, autónomo + RETA, правила 2025–2026 с источниками,
   119 тестов. В ignidash этого нет, в форке ядро пришлось бы переписать на TypeScript.
2. **Американская логика в ignidash — не отдельный слой.** Американские идентификаторы есть в 95 из 455
   файлов. В движке на такие файлы приходится 5,6 из 7,9 тыс. строк (71 %): счета 401k/Roth/HSA, порядок
   изъятий по возрасту 59½, RMD, лимиты IRS, налогообложение выплат Social Security, база по средней цене
   вместо FIFO. Доход self-employment (наш autónomo) отклоняет валидация: «This income type is not yet
   supported».
3. **Инфраструктура SaaS.** Next.js + Convex (база и серверные функции) + Better-Auth + Stripe + PostHog +
   Azure OpenAI. Локально — Convex-бэкенд и регистрация в собственном приложении. Интерфейс только
   английский, i18n нет.
4. **Разработка upstream остановилась.** Один автор: 700–950 коммитов в месяц в июле–октябре 2025,
   12 в марте 2026, после 16.03.2026 — только обновления зависимостей. Последний релиз — v0.1.13
   (бета, 24.02.2026). Форк будет жёстким: 73 тыс. строк чужого TypeScript станут нашими.

**Рекомендую вариант B:** продолжать свой проект, а ignidash использовать как справочник — брать из него
структуру движка, алгоритмы и UX в шаги 5, 6 и 8. Если NiceGUI станет узким местом, позже можно поставить
React-фронт поверх `planner.reports` (вариант C), не забирая у ignidash движок и инфраструктуру.

Если всё же форк — план ниже (вариант A). Он начинается с дешёвой проверки go/no-go, так что решение
легко откатить.

## ignidash: факты

| | |
|---|---|
| Что это | Веб-планировщик пенсии в духе ProjectionLab: планы, счета, доходы и расходы, долги, недвижимость; детерминированный прогон, Monte Carlo, исторический бэктест, AI-чат |
| Стек | Next.js 16, React 19, TypeScript, Tailwind 4, Zustand, React Hook Form + Zod 4, Recharts; Convex; Better-Auth; Stripe; PostHog; Azure OpenAI |
| Лицензия | AGPL-3.0 |
| Объём | ~73 тыс. строк TS/TSX с тестами. Движок `src/lib/calc` — 7,9 тыс. строк кода и 22,6 тыс. строк тестов; UI — 27 тыс. строк. 1 221 unit-тест (Vitest), 3 e2e-спецификации (Playwright) |
| Активность | С 04.07.2025, 5 337 коммитов, один автор. 284 звезды, 26 форков, 16 открытых issues и PR |
| Запуск | `npx convex dev --local` + `npm run dev`; self-host — Docker Compose (Convex backend, Convex dashboard, приложение) и регистрация на `/signup` |

Как устроен движок:

- `simulation-engine.ts` считает по месяцам, налог — раз в 12 месяцев. Отсчёт идёт от текущей даты,
  поэтому налоговый год — это 12 месяцев от запуска, а не календарный год.
- Налог досчитывается итерациями (`settleTaxes`: до 10 итераций, порог $1): изъятия на уплату налога
  создают новый налог. Состояние переноса убытков сохраняется и восстанавливается между итерациями.
- Отдельный процессор на каждую область: доходы, расходы, долги, физические активы, портфель (взносы
  и изъятия), налоги, доходность.
- Налоговые таблицы — константы 2026 года в `tax-data/*.ts`. Измерения «год» и индексации нет.
- Восемь американских типов счетов. База taxable-счёта — средняя цена (pro-rata); ребалансировка внутри
  него реализует прирост.
- Взносы — «водопад» правил с приоритетами и лимитами (лимиты IRS, employer match, Mega Backdoor Roth).
- Порядок изъятий зашит и зависит от возраста 59½ (`portfolio.ts`, `getWithdrawalOrder`). Настраиваемый
  порядок есть в roadmap, но не сделан.
- Доходность: фиксированная; стохастическая (корреляции через разложение Холецкого, акции —
  логнормально); исторический бэктест на данных NYU Stern (S&P 500, облигации и векселя США, инфляция
  США, с 1928 г.).
- Хранение в Convex: планы, `finances` (текущие активы и долги, без истории), снимки плана для undo.
  Расчёт идёт в браузере, в пуле web-воркеров.

## Варианты

- **A. Жёсткий форк ignidash.** Ядро переписываем на TypeScript, американские счета, налоги и правила
  меняем на испанские, SaaS-части вычищаем.
- **B. Свой проект, ignidash — справочник.** Python и NiceGUI остаются. Движок, Monte Carlo и экраны
  пишем сами, перенося из ignidash идеи, алгоритмы и UX.
- **C. Потом и только при необходимости: React-фронт поверх нашего ядра.** FastAPI отдаёт данные
  `planner.reports`, фронт на React + Recharts по образцу экранов ignidash. Движок и налоги остаются на
  Python. Это надстройка над B, а не альтернатива ей.

Гибрид «UI ignidash + наш Python-движок» не рассматриваю. UI ignidash завязан на хуки Convex, Zod-схемы
американских счетов и TS-движок в web-воркерах: переписывать пришлось бы слой данных и почти все формы,
то есть делать тот же C, но с чужим багажом. Вызывать Python-налог из TS-движка тоже не выйдет:
500 прогонов × 40 лет × до 10 итераций gross-up — до 200 тыс. вызовов на один Monte Carlo.

## План A: форк ignidash

Принципы:

- Отдельный репозиторий (например, `E:\GameDeveloping\ignidash-es`), upstream — второй remote.
  Подтягивать изменения из upstream не планируем: после фазы 2 код разойдётся слишком сильно.
- `spain-planner` остаётся эталоном: Python-ядро выгружает golden-фикстуры, TS-порт должен совпадать
  с ними до цента.
- `rules/<год>/*.yaml` переносятся как есть: правила остаются данными с источниками, чисел в коде нет.
- Каждая фаза — вертикальный срез (данные → движок → экран → тесты) и закрывается зелёными
  `npm run test:once`, `npm run typecheck`, `npm run lint`.

### Фаза 0. Проверка go/no-go

Цель — до любых переделок убедиться, что ignidash работает у нас локально и приватно.

Проверки (learning tests):

- `npx convex dev --local` работает без аккаунта Convex, данные лежат на диске;
- Next.js и Convex слушают только `127.0.0.1` (`next dev -H 127.0.0.1`);
- при работе в приложении нет исходящих запросов (DevTools → Network): PostHog, Vercel Analytics, Stripe,
  Resend и Azure OpenAI выключены;
- регистрация по email и паролю работает без почтового сервиса;
- `npm run test:once` зелёный на Windows — базовая линия 1 221 тест.

Что сделать: убрать маркетинговые страницы, pricing, legal, вебхуки Stripe, PostHog и Vercel Analytics;
скрыть AI-чат и insights.

**Условие перехода:** все проверки пройдены. Если какая-то не проходит и быстро не чинится — остановиться
и перейти к B.

### Фаза 1. Сквозной срез: autónomo → IRPF и RETA → экран налогов

Самый тонкий путь через все слои: один профиль (autónomo, cash-счёт, расходы) проходит с испанскими
налогами от формы ввода до графика. Американские счета пока остаются, но в профиле не участвуют.

Компоненты:

- `src/lib/calc/es-tax/` — порт `planner.tax`: шкалы, mínimos, reducciones, compensación, `irpfAnual`,
  `actividad` (rendimiento neto ↔ cuota RETA). Функции скалярные: движок ignidash считает по одной
  траектории.
- `rules/<год>/*.yaml` и загрузчик со схемами Zod: `rulesForYear(year)`, `indexed(factor)`.
- `SpanishTaxProcessor` с контрактом `TaxProcessor` (`process`, `saveCarryoverSnapshot`,
  `restoreCarryoverSnapshot`), чтобы итерации `settleTaxes` работали без изменений. Налог считается по
  календарным годам, первый год неполный.
- Налоговые настройки: вместо `filingStatus` — состав семьи для mínimos (как `Persona` и `Familiar` у нас).
- Доход `autonomo` вместо заблокированного `selfEmployment`: facturación, gastos; RETA и IRPF — в годовом
  расчёте.
- `TaxesData` в испанской структуре: bases, cuotas по половинам, mínimos, reducciones, RETA, pendientes.
  Под неё переделать налоговые части `chart-data-extractor.ts`, `table-data-extractor.ts`,
  `key-metrics-extractor.ts`, `simulation-data-extractor.ts` и налоговые экраны.
- Валюта — EUR в `CURRENCY_CONFIG` (`src/lib/utils/number-formatters.ts`).
- В `spain-planner`: скрипт выгрузки golden-фикстур — входы и результаты `irpf_anual` и `actividad` по сетке
  сумм, составов семьи и годов 2025–2026.

Тесты: golden-фикстуры (допуск 0,01 €); перенесённые тесты шкал, mínimos и compensación; тест движка на
эталонном профиле за 2–3 года.

**Условие перехода:**

- [ ] TS совпадает с Python на всей сетке фикстур;
- [ ] доход autónomo сохраняется в Convex и доходит до движка;
- [ ] экран налогов показывает IRPF estatal/autonómica и RETA по годам, американских полей на нём нет.

### Фаза 2. Испанские счета и движение денег

Компоненты:

- Типы счетов: `cash`; `fondo` — traspaso без налога; `etf` — лоты FIFO, дивиденды ежегодно в базу
  сбережений; `planPensiones` (PPI/PPES) — взносы уменьшают общую базу в пределах лимитов из
  `reducciones.yaml`, выплаты облагаются как rendimientos del trabajo. Схемы Zod, валидаторы Convex,
  классы в `account.ts`, формы ввода.
- Удалить Roth, HSA, 403b/IRA, RMD (`rmd-table.ts`), штрафы за раннее изъятие, NIIT, налогообложение
  Social Security, Section 121.
- `contribution-rules.ts`: лимиты IRS заменить лимитами LIRPF из YAML.
- `portfolio.ts`: настраиваемый порядок изъятий (по умолчанию cash → fondos → ETF → plan de pensiones);
  ребалансировка внутри fondos — traspaso без налога, продажа ETF — с налогом.
- Перенос убытков — через наш `compensacion` (4 года, 25 %) вместо американских правил.
- Миграции Convex не пишем: база локальная, её проще пересоздать.

Тесты: FIFO (частичная продажа, несколько лотов), traspaso без налогового события, лимиты PPES и 30 %,
выплата из плана как trabajo, compensación на golden-фикстурах.

**Условие перехода:**

- [ ] эталонный план со всеми четырьмя типами счетов считается на 30 лет;
- [ ] инварианты по годам: net worth = счета − долги; реализованный прирост = сумма по лотам;
- [ ] поиск американских идентификаторов по `src/lib/calc` ничего не находит.

### Фаза 3. Планы в духе ProjectionLab

Компоненты:

- Milestones (год, возраст, условие «net worth ≥ X»); начало и конец доходов и расходов привязываются к ним.
- Сравнение двух планов вместо заглушки: кривые net worth, налоги, success rate.
- Spending rules: фиксированная реальная сумма, % портфеля, Guyton–Klinger.
- Недвижимость по-испански: ITP, IBI, exención por reinversión en vivienda habitual вместо Section 121,
  imputación de rentas. Кредиты берём из ignidash.
- Политика проекции правил `frozen | indexed` в настройках плана; пенсия Seguridad Social — входной доход.

**Условие перехода:**

- [ ] два плана сравниваются бок о бок;
- [ ] milestone по условию срабатывает в тесте движка;
- [ ] продажа vivienda habitual с реинвестицией не создаёт прироста в базе сбережений.

### Фаза 4. Monte Carlo в евро и Progress

Компоненты:

- Исторические ряды в евро (акции, облигации, инфляция в Испании) — файлы данных с источниками;
  параметры стохастической модели — по ним. Данные NYU остаются опцией.
- Определение «успеха» — параметр плана.
- Progress: история net worth (новая таблица снимков), график план-факт, импорт из SQLite-базы Wealthfolio.

**Условие перехода:**

- [ ] бэктест на рядах в евро совпадает с ручным расчётом на коротком окне;
- [ ] сумма после импорта из Wealthfolio совпадает с тем, что показывает сам Wealthfolio.

### Порядок фаз

```
Фаза 0 (go/no-go)
  ↓
Фаза 1 (сквозной срез)
  ↓
Фаза 2 (счета)
  ↓
Фаза 3 (планы)   ∥   Фаза 4 (Monte Carlo, Progress)
```

Фазы 3 и 4 затрагивают разные модули и могут идти параллельно.

Сквозные вопросы:

- Язык интерфейса — решение за вами (см. ниже). i18n на весь UI — отдельная большая работа.
- AI-чат и insights выключены. Перевод на Claude API с контекстом испанских налогов — вне плана.

| 5.1 Движок и ledger | `simulation-engine.ts`: процессор на каждую область, годовой `SimulationDataPoint` | Шаг — год, а не месяц; `SimulationDataPoint` — чек-лист колонок ledger |

| 5.4 Flows и изъятия | `contribution-rules.ts` (приоритеты, лимиты, привязка к доходу, счёт для излишка); `portfolio.ts` (порядок изъятий, дефицит и его погашение) | Режимы `max`, `percent_remaining`, `fixed`, `until_balance`; порядок изъятий — из сценария |
| 5.5 Недвижимость, кредиты | `debts.ts`, `physical-assets.ts` (0,8 тыс. строк) и их тесты (4,6 тыс. строк) | Налоги — ITP, IBI, exención por reinversión |
| 6 Monte Carlo | `stochastic-returns-provider.ts` (Холецкий, логнормальные акции), `lcg-historical-backtest-returns-provider.ts`, `seeded-random.ts`, `multi-simulation-analyzer.ts` | Векторизация по траекториям `(n_trials,)`; ряды в евро |
| 8 UI | Раскладка «ввод — результаты», набор графиков и таблиц, детализация года, перцентили Monte Carlo, undo через снимки плана | NiceGUI + Plotly; undo — история версий YAML-сценария |
| Тесты | Названия ~1 200 тестов как каталог краевых случаев | pytest на наших моделях |

Не берём: месячный шаг (годового хватает для модели на 20–30 лет), движок по одной траектории
(у нас векторизация), Convex, авторизацию, AI.

Лицензия: идеи и алгоритмы берём свободно, код дословно не переносим (перевод на Python — тоже
производная работа), пишем своё по мотивам.
